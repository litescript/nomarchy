# Storage and boot archaeology — caesar and rigel

Read-only investigation, 2026-09-27, before designing caesar's final cutover. Nothing was
written to any ESP, NVRAM variable, partition table, bootloader config, LUKS header or
filesystem. The old NVMe's ESP was read from its **verified NAS image**
(`Backups/images/caesar-omarchy-esp/`), not from the partition, with a small read-only FAT32
reader, so the target disk was never mounted.

The source model this serves:

| source | role |
|---|---|
| SATA Nomarchy (`sda2`) | live source of current user data; stays installed and untouched as the fallback |
| NAS raw image of the XPG NVMe | permanent, verified archive of old Omarchy (digest match, scrub clean) |
| Git / nomarchy | declared machine policy and config |
| backups | protected user data |

The XPG NVMe is the **target**. It is destroyed at cutover and is not a source afterwards.

### The two ESPs

**`sda1` (SATA disk, 511M, 41% used)** — shared by three generations:

- `EFI/systemd/systemd-bootx64.efi` and `EFI/BOOT/BOOTX64.EFI`: **systemd-boot 261.2**, SATA
  Nomarchy's loader and the one the firmware entered this boot. One Type #1 entry,
  `nomarchy.conf` (`root=UUID=5a369b57… rw`), `vmlinuz-linux` + `amd-ucode.img` +
  `initramfs-linux.img` on the ESP itself. `loader.conf`: `timeout 5`, `editor no`.
  systemd-boot also lists **Windows automatically** (`auto-windows`, same ESP).
- `EFI/Microsoft/Boot/`: **Windows Boot Manager** (`bootmgfw.efi`, BCD, logs back to
  2024-04) and `EFI/Microsoft/Recovery/`. Windows' boot files live **here**, on the SATA disk.
- `EFI/ubuntu/`: shim + GRUB of the **Ubuntu install `sda2` held before SATA Nomarchy**. Its
  `grub.cfg` searches for filesystem `0686cb60-…`, which was reformatted away: **dead**.
- `EFI/BOOT/fbx64.efi`, `mmx64.efi`: shim fallback/MokManager, also Ubuntu leftovers.

**`nvme1n1p1` (XPG, 2G)** — Omarchy's, read from the NAS image:

- `EFI/Limine/limine_x64.efi` (+ `.bak`), `EFI/BOOT/BOOTX64.EFI` (Limine as fallback),
  `BOOTIA32.EFI`.
- `EFI/Linux/omarchy_linux.efi`: a **290 MB unified kernel image**.
- `limine.conf`: one Omarchy entry (`quiet splash cryptdevice=PARTUUID=8bd201c0…:root
  root=/dev/mapper/root rootflags=subvol=@ …`) with **five bootable Snapper snapshots**
  generated by **limine-snapper-sync**, each a stored older UKI under
  `54e4d06f…/limine_history/` plus `rootflags=subvol=/@/.snapshots/N/snapshot`. The only
  chainload entry is Limine's own `EFI/BOOT/BOOTX64.EFI` fallback. **No Windows entry.**
- **No `EFI/Microsoft` at all.** Nothing Windows needs lives on the disk being erased.

### The pre-install boot backup

In the repo: **`docs/migration/caesar-boot-backup/`** (45 MB, 468 files, committed
`06efa2c` on 2026-09-09). It contains a copy of `sda1`'s `EFI/` tree (Windows, Ubuntu shim
and GRUB), Ubuntu's `/boot/grub` and generated `grub.cfg`, `grub.d/`, `sda`'s `sfdisk`
dump, `lsblk` and `blkid` before the SATA install, `efibootmgr -v` before and after a
Limine test, Omarchy's kernel cmdline, `mkinitcpio.conf` and `nvidia.conf`, Ubuntu's
`fstab`, and a hardware "known good" snapshot. It does **not** contain the XPG's ESP; the
verified NAS image does, byte for byte.

### What erasing the XPG takes with it

- `Boot0001` and `Boot0003` become dangling NVRAM entries (harmless; to be removed).
- Omarchy's Limine, UKIs and snapshot entries — all in the NAS image.
- **Nothing Windows needs**, and nothing SATA Nomarchy needs: both boot from `sda1`.

`quiet splash` on the cmdline, the `plymouth` hook before `sd-encrypt`. From this boot's
journal: Plymouth's screen at 1.19 s; *Forward Password Requests to Plymouth* at 1.23 s (the

**The `rigel` theme is two hand-written files, owned by no package and absent from the
repo**: `/usr/share/plymouth/themes/rigel/{rigel.plymouth,rigel.script}` (2026-09-15), a

`/.snapshots` is mounted from `@snapshots` and **empty**. Rigel has never taken a snapshot;
the only bootable snapshots in this history were Omarchy's (Limine + limine-snapper-sync).

**Rigel's NVRAM is dirty, and it boots by accident of the fallback path.**
`BootOrder: 0007,000B,000A,0000,…`, `Timeout: 0`. The first three — two "Omarchy" UKIs and
"Limine" — point at files that no longer exist on the ESP. The firmware skips them and lands
on `Boot0000`, a Dell auto-created entry for `\EFI\Boot\BootX64.efi` — the *fallback copy* of
systemd-boot. systemd-boot itself was never registered (`bootctl install` would have added a
"Linux Boot Manager" entry). `Boot0004` (fwupd) points at a partition on no current disk.
Also: `systemd-boot-update.service` is disabled, so the ESP carries systemd-boot **261.3**
while the installed `systemd` is **262**.

## Proposed final caesar layout

Starting point: rigel's model (GPT, 2G ESP, LUKS2, flat btrfs subvolumes, systemd-boot,
`sd-encrypt` + Plymouth), corrected by what this investigation found. **Nothing below is
applied; it is for review.**

### Target identity — the only thing a destructive step may act on

`/dev/disk/by-id/nvme-XPG_SPECTRIX_S40G_2K0420036195`, and only if the device behind it
reports model `XPG SPECTRIX S40G`, serial `2K0420036195` and size 953.9G (1,024,209,543,168
bytes). Anything else — including every `/dev/nvmeXn1` name — is refused.

### Layout

| | proposal | why |
|---|---|---|
| partition table | GPT | as every disk here |
| p1 | **ESP, 2 GiB, FAT32**, type EF00, PARTLABEL `caesar-esp` | rigel's and Omarchy's size: room for kernels, a fallback initramfs, and UKIs later. **caesar's own** — not `sda1` |
| p2 | rest (~951.9G), type **8304 Linux root (x86-64)**, PARTLABEL `caesar-root` | the discoverable-partitions type rigel and Omarchy already use |
| encryption | **LUKS2** on p2, label `caesar-luks`, cryptsetup defaults (argon2id, aes-xts-plain64, 512-bit), `--sector-size 4096`; passphrase keyslot **plus a recovery key** (`systemd-cryptenroll --recovery-key`) kept offline | encrypted as asked; a recovery key is the difference between a forgotten passphrase and a restore from backup |
| mapping | `cryptroot`, unlocked from `rd.luks.name=<LUKS UUID>=cryptroot`, `rd.luks.options=discard`; no crypttab for root | rigel's scheme; TRIM through LUKS on an SSD |
| filesystem | **btrfs**, label `caesar`, `noatime,compress=zstd:3,space_cache=v2` (ssd auto-detected) | rigel's options |
| `@` | `/` | |
| `@home` | `/home` | |
| `@var_log` | `/var/log` | logs survive a root rollback |
| `@pkg` | `/var/cache/pacman/pkg` | keeps GBs of package cache out of every root snapshot, and rollback from rolling the cache back (rigel dropped it; caesar's cache is large) |
| `@snapshots` | `/.snapshots` | **top-level**, not nested in `@` as on Omarchy — rolling `@` back must not take its own snapshots with it |
| nested, not snapshotted | `~/.local/share/docker` (rootless docker data), optionally `~/Downloads/torrents` | btrfs snapshots stop at nested subvolumes: churn and image layers stay out of `@home` snapshots (Omarchy did this for torrents) |
| swap | **none on disk**: zram (already declared for caesar); no hibernation | caesar is an always-on desktop with sleep masked |

### Boot

| | proposal | why |
|---|---|---|
| loader | **systemd-boot** on the NVMe's own ESP, **registered in NVRAM** (`bootctl install` → "Linux Boot Manager", first in `BootOrder`), `systemd-boot-update.service` **enabled** | what rigel and SATA caesar already run; rigel shows what not registering and not updating costs |
| entries | Type #1: `vmlinuz-linux` + `amd-ucode.img` + `initramfs-linux.img`, plus a **fallback initramfs** entry | caesar has none today (`PRESETS=('default')`); one bad initramfs should not need a rescue boot |
| initramfs | mkinitcpio, `HOOKS=(base systemd autodetect microcode modconf kms keyboard sd-vconsole plymouth block sd-encrypt filesystems fsck)`, `MODULES=()` | rigel's, verbatim; the late-KMS NVIDIA decision (audit §10) stands |
| unlock | **Plymouth**, with the `rigel` theme brought into the repo and a caesar variant of it | the unlock screen Pete liked, made reproducible |
| Windows | stays on `sda1`, untouched; reached by the firmware menu or a `reboot-windows` script (`efibootmgr --bootnext 0000` + reboot) | systemd-boot lists Windows only from its *own* ESP; copying Microsoft's files onto the NVMe would drift with every Windows update |
| SATA fallback | `Boot0005` (sda1's systemd-boot) stays in NVRAM, second in order | the immediate fallback; untouched |
| NVRAM cleanup | delete `Boot0001`, `Boot0003` (Omarchy, gone with the wipe) and `Boot0002` (dead Ubuntu) | part of the reviewed cutover plan, not before |

### Snapshots: Snapper, and one decision for Pete

**Snapper** on `@` (`/.snapshots`) with **snap-pac** (a pre/post pair around every pacman
transaction), timeline snapshots, and optionally a `home` config. Rigel has none of this, so
it is new — the model comes from Omarchy.

**Bootable snapshots are a bootloader choice**, and the one real fork in this proposal:

- **systemd-boot + Snapper (recommended).** Snapshots are for *recovery*: roll back from a
  running system, or — if caesar will not boot — from the **SATA Nomarchy install, which is
  a complete, always-present rescue system on this machine**. One bootloader across the
  fleet, the one both hosts already run.
- **Limine + limine-snapper-sync** (Omarchy's model): every snapshot bootable from the
  menu. Worth it on a machine with no second OS; caesar has one. Costs a second bootloader
  to maintain in nomarchy and two AUR packages.

Worth also knowing: **TPM2 is present on both hosts**, so passphrase-less unlock
(`systemd-cryptenroll --tpm2-device`) is possible — but with Secure Boot off, a TPM binding
protects less than it appears to. Not proposed; noted.

### What the repo should hold (verification, not provisioning)

- `hosts/caesar/storage/` — the layout above as data: target by-id, model, serial, size;
  partitions (type, size, PARTLABEL); LUKS2 label and parameters; btrfs label, subvolumes,
  mountpoints, options; loader, cmdline, HOOKS.
- A **read-only verifier** in `nomarchy status`: is `/` on the declared LUKS/btrfs, are the
  subvolumes mounted with the declared options, does `/proc/cmdline` match, is systemd-boot
  the registered first NVRAM entry and current, is the Plymouth theme installed.
- A **separate, human-run provisioning script** — never part of `nomarchy install` — that
  refuses any disk whose by-id, model, serial and size do not all match, prints the complete
  destructive plan, and requires the serial typed back before it touches anything. It can
  run **from SATA Nomarchy itself** (the XPG is not in use by it; `arch-install-scripts` is
  already installed), which removes the need for a USB installer.
- The VM rehearsal extended down to it: OVMF firmware, a virtual disk carrying the XPG's
  model/serial so the identity check is exercised, provisioning, then the existing
  base → desktop → host → link. One open question for an unattended release-candidate
  run: the LUKS passphrase at boot (a VM-only keyfile or an emulated TPM, never on metal).

### Fix eventually: the tty1 flash between unlock and desktop

Pete's note: between the Plymouth unlock and the desktop, the autologin tty pokes through for
a split second. Not a blocker. The flash has three sources, each with a known lever, to try
on the real screen (caesar's NVIDIA takes the display late — `MODULES=()` — so what works on
rigel's Intel panel may not carry over as-is):

- **agetty's own output** on tty1 — the issue banner and the autologin line. The autologin
  drop-in can pass `--noissue --nohostname --skip-login` (and keep `--noclear`).
- **bash's login chatter** — an empty `~/.hushlogin`.
- **Plymouth letting go too early** — `plymouth quit --retain-splash` (a drop-in for
  `plymouth-quit.service`) keeps the last splash frame on screen until the compositor
  becomes DRM master, so there is nothing to see between the two.
  `vt.global_cursor_default=0` (rigel already has it) hides the cursor meanwhile.
